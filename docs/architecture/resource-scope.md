# Resource scope: request and job integration (bounded rollout)

## Status and delivery boundary

This extends the Projects implementation already merged in PR #119. Baseline
main commit: `0dec12c7b4700ab187b9cfb27e1f45866d3ae391`; baseline tracked tree:
`d47b99cc817407c34f423ce745abfa621425e986`.

Implemented here: persistent resource ownership, validated request scope,
SQL filtering, explicit provider/credential assignments, saved job scope,
worker/scheduler reauthorization, guarded inventory reconciliation and console
capability reauthorization. **This is not the complete governance subsystem.**

There is deliberately no switch that enables unrestricted tenant execution:
`PROJECT_EXECUTION_REQUIRES_PLATFORM_ADMIN` blocks delegated resource execution
outside Default, and also blocks legacy delegated execution once non-default
managed resources exist. An explicit global `governance.admin` grant, bounded by
the token's existing scope, is required for those execution paths. Administrative
read access and scoped resource metadata APIs do not acquire that grant.

The gate is necessary because arbitrary Terraform image/VM references, Ansible
host targets, provider-native actions and all external adapters have not yet
been admitted through a complete policy/placement/quota pipeline. Removing the
gate without implementing and testing those boundaries is unsafe.

Single-project Default installations retain prior execution permissions.
Direct synchronous Proxmox VM/task/restore routes are Default-only; they are
also rejected when the provider has records owned by another project, even for
platform administrators. Use the existing deployment/job path, which records its
scope, for supported platform-admin project operations.

No Project Switcher or claim of complete browser multi-tenancy is added here.
The existing UI continues to send Default requests unless a client explicitly
uses the context contract below. Static repository template/playbook catalog
entries remain globally configured; per-project catalog/image grants are pending.

## Domain and shared composition

`app/resource_scope/` owns ownership columns/constraints, live authorization,
scoped session behavior, assignment models/services, HTTP composition and console
checks. `app/modules/feature_resource_scope.py` discovers its thin router.

The existing resource models acquire a cross-cutting ownership mixin. Existing
HTTP modules import the scoped dependency without replacing their endpoints.
`app/database.py` constructs the scoped session subclass. Identity, tenancy,
project, audit and event-administration APIs retain their existing authorization
contracts. No role name or username is an authorization check.

## Ownership and migration

The additive migration `b752ca806e19`, parent `9a42d10e63bc`, adds non-null
`tenant_id` and `project_id` to:

- deployments and jobs;
- managed_vms and managed_resources;
- blueprints;
- hostname_schemes and hostname_reservations;
- ip_pools and ip_allocations;
- scheduled_operations.

Every legacy row receives Default/Default. Original users, password hashes,
credential ciphertext, resource identifiers and global role assignments are
preserved. Existing provider/credential identities receive Default assignments
without duplicating their secrets. Missing compatibility memberships are added
without reactivating disabled memberships or creating permission grants.

New users receive Default memberships at creation, not on login. Removed
memberships/assignments are not regenerated by authentication. Newly created
central credentials/providers are assigned to the authenticated creation scope
(Default for existing clients). Implicit infrastructure assignment additions and
central deletions advance affected project revisions, so stale allowlist
replacement fails rather than dropping a concurrently added reference.

Composite foreign keys verify the tenant/project pair, and parent-child keys
verify job/deployment, VM/deployment, resource/deployment, schedule/deployment,
allocation/pool, reservation/scheme and retry-job scope. Legacy single-column
foreign keys are retained alongside the new checks. Specify explicit join ON
clauses where multiple foreign-key paths are possible.

ORM ownership is immutable. Maintenance writes inherit a deployment/pool/scheme's
scope, not an operator's last selected project. Unadopted inventory records may
receive explicit ownership through trusted maintenance code; the validated HTTP
request cannot supply arbitrary ownership fields to the old input schemas.

Project deletion refuses existing resource rows, operational history or
infrastructure assignments. This is conservative: destroyed-resource history
still prevents deletion until a separate audited retention operation exists.
Downgrade refuses non-default resource ownership or assignments rather than
silently flattening security domains. It otherwise removes only the new resource
ownership/assignment schema, retaining the old data and tenancy/projects tables.

## Request context and effective permissions

Existing resource endpoints accept either this pair of headers:

```http
X-Tenant-ID: <tenant UUID>
X-Project-ID: <project UUID>
```

or paired `tenant_id` / `project_id` query parameters. Headers and query values
must agree. Repeated fields, incomplete pairs and malformed UUIDs return 422.
Omitting both selects Default/Default. An inaccessible or mismatched explicit
scope returns 404; it never silently falls back to Default. The header/query
contract is included in the existing endpoints' OpenAPI descriptions.

For delegated access the account/token, tenant membership, project membership,
parent status, current roles and assignment-time permission ceilings are checked.
Tenant resource grants inherit within their own tenant. Global resource grants
apply within a membership or under explicit global governance administration.
API token scopes remain an upper bound. Disabled parents are not usable for
resource APIs; suspended parents reject writes. A global administration API can
recover their state but resource execution cannot ignore it.

Resource permissions are delegated using the existing Role/Permission catalog.
They are never copied into `/auth/me`'s global permissions or reused to authorize
identity administration. Existing role customizations and assignment ceilings
are not silently expanded during upgrade. Explicit role edits/reassignments and,
where needed, token reissue are required to grant newly intended powers.

Scope writes reuse the governance lock, then re-read authorization. This is a
correctness boundary rather than a throughput optimization: long synchronous
legacy operations may hold the existing shared governance lock. Dedicated
operation-level locking and provider work outside request transactions remain
part of the governed-operation work.

## SQL and identity-map isolation

Only the authenticated dependency and reauthorized worker bind a resource
session. An already bound transaction cannot change scope. Binding rejects
cached foreign resource objects, cached inaccessible provider/credential objects,
and cached indirect child data, preventing identity-map `get()` shortcuts.

ORM SELECT, count, alias, join, UPDATE and DELETE statements receive resource
criteria before pagination. Providers/credentials require assignment references;
job logs and Terraform state/plan records require a same-scope parent. Raw SQL,
Core statements and bulk inserts through a bound session are rejected. Bulk
ownership updates are rejected; database composite keys protect parent changes.

An unbound maintenance session is privileged internal code, not a public API.
Direct connection access is restricted here to minimal ownership/existence
checks and atomic reference registration. It is not an authorization escape hatch
for route code. Extending this to a database RLS boundary or arbitrary third-party
SQL execution is outside this patch.

## Infrastructure assignment API

```http
GET /api/v1/projects/{project_id}/infrastructure-access?limit=100&offset=0
PUT /api/v1/projects/{project_id}/infrastructure-access
```

GET verifies visibility and returns tenant/project, project revision, bounded
provider/credential ID pages, separate totals, limit and offset. The maximum
page is 200. IDs are references; no decrypted secrets are returned.

PUT requires both global `governance.admin` and `governance.access.manage`.
It atomically **replaces** the allowlists, requires `expected_version`, accepts
at most 200 IDs per list and verifies every provider's credential is explicitly
included. Do not construct replacement lists from a single partial GET page;
read all pages or supply an intentional complete policy. Very large allowlists
need a future batch-delta management API, not an unbounded request body.

```json
{
  "expected_version": 2,
  "provider_ids": [10],
  "credential_ids": [20]
}
```

Missing references fail with a controlled error. Changing assignments emits the
existing transactional audit/business event `project.infrastructure_access.changed`.
Cross-tenant assignment changes require platform authority; tenant managers
cannot obtain an unassigned credential by guessing its ID.

## Idempotency and asynchronous execution

Non-default idempotency fingerprints include tenant/project. Default keeps its
legacy fingerprint format. Same-key cross-project reuse conflicts instead of
returning or creating another project's result. Replay reauthorizes the current
scope, verifies the stored result's resource identity and relevant references,
and adds ownership fields to old Default deployment/job responses without
changing their saved status, timestamps or identifiers.

Workers use the job's persisted ownership, never later HTTP headers or a user
preference. Existing API-token expiry and browser refresh-family rules remain.
A token must belong to the recorded job owner. Before the executor runs, live
project permissions, rollout gates, provider assignment, credential assignment,
Ansible credential references and job/deployment consistency are verified.
Heartbeat checks reauthorize again (at the existing one-second check cadence).
External operations already accepted by a provider are not retroactively undone.

Scheduled jobs verify the schedule/deployment pair and current scoped execution
permissions before creation. Jobs created from a deployment inherit its scope.
Recovery/inventory sessions preserve that recorded ownership. Permission
revocation does not prevent writing failure/cleanup status on unchanged resource
references; it prevents starting/continuing the executor at its check points.

## Provider responses, inventory and console capability checks

Provider VM lists cannot be protected solely by ORM criteria. Returned native
identities are matched against minimal ownership records in bounded batches.
A shared provider's unattributed VMs are hidden, including the interval between
provider creation and inventory registration. Untracked VMs remain discoverable
only in an exclusively Default provider. Missing/ambiguous ownership does not
become cross-project visibility.

Inventory import rejects a known foreign VM before asking the provider for its
details. Synchronization and delayed raw-task reconciliation cannot move or
replace an existing foreign VM. Raw-task records are acknowledged in Redis only
after database commit; per-item savepoints retain failed reconciliation records.
No new broker or job queue is introduced.

Console capabilities now record actor, token and project identifiers. Assets
and WebSocket establishment reauthorize them. Active WebSockets recheck the
capability and permissions every five seconds and close on expiry/revocation.
Pre-upgrade capabilities without the ownership/principal fields expire rather
than bypassing the new checks. The existing short-lived bearer capability design
is retained; this is not a replacement authentication mechanism.
